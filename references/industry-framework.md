# 行业研究框架：定义与边界 → 五维 → 关系解释 → 建议

本文件展开 [SKILL.md](../SKILL.md) 的核心研究主线，是撰写 `report.md` 五维总览、填写 `evidence.json` 的 `coverage`/`claims[].dimensions` 时的方法参考。数据结构定义见 [evidence-schema.md](evidence-schema.md)，执行节奏见 [research-workflow.md](research-workflow.md)。

## 1. 先建一张行业定义卡

在展开五维研究前，先回答五个问题，建立最小边界共识：

| 问题 | 要点 |
|---|---|
| 服务谁？ | 区分购买者、使用者、付款者、采购影响者；只记录与行业有关的特征，不默认补人口/收入画像 |
| 提供什么？ | 产品、服务或混合交付，以及主要细分类别 |
| 解决什么问题？ | 具体任务和价值；企业宣称的价值 vs 用户验证的价值分别标记 |
| 市场大致多大？ | 先记录可用指标、口径与缺口，随后在"市场"维度核验；未知不阻塞后续研究 |
| 边界在哪里？ | 纳入、排除、交叉领域，防止把相邻产业全部计入 |

容易混淆、需要在这一步就澄清的口径：软件许可收入 vs 软硬件总收入 vs 实施服务收入；行业规模（市场空间）vs 交易总额（GMV）vs 企业营业收入 vs 融资额；企业数量 vs 门店/网点数量 vs 从业人员数量。这些是口径规则，不是任何具体行业的数据结论。

## 2. 五维研究骨架

行业地图、交易与交付、用户与渠道等问题嵌入下面五个维度，不再单独建立第六个模块。缺资料的维度保留"资料不足"（`coverage` 中标 `missing`），不能为了填表编造。

| 维度代码 | 核心问题 | Quick 的最低可用输出 |
|---|---|---|
| `market` | 规模、变化、细分需求和发展阶段如何？ | 一个有口径的规模/需求指标或明确缺口，加增长或阶段的有限判断 |
| `value_chain` | 产品、服务和资金如何流转，关键资源由谁掌握？ | 关键角色、交易方向、瓶颈或议价问题 |
| `business_model` | 客户为什么付费，收入和成本如何形成，盈利取决于什么？ | 一条代表性交易的收费与交付逻辑，加主要盈利条件 |
| `competition` | 谁在竞争或合作，集中度、壁垒和替代关系如何？ | 代表性玩家类型、可核实的关系与差异；不强求份额排名 |
| `trends_risks` | 哪些变化影响哪些环节，判断成立需要什么条件？ | 一个重要变化及其可能影响、反证或待验证项 |

用户只要求某个维度时按其范围完成，其余维度在 `coverage` 中标 `out_of_scope` 并说明范围依据，不强制扩写成完整行业报告。一条主张可以同时关联多个维度（`claims[].dimensions` 允许多值），例如"某项成本变化如何影响下游定价"这类推断天然横跨 `value_chain` 与 `trends_risks`。

### 2.1 market：市场与发展阶段

- 优先选与边界匹配的规模、销量、客户数、渗透率或需求指标，说明为什么使用该指标。
- 有可靠规模数字时记录统计主体、年份、地区、范围和测量方法；没有时可说明需求代理信号及其限制，不把搜索热度、融资额当作行业收入。
- 增长拆分可观察的驱动（销量、价格、渗透率、客户数量、使用频次），仅在口径一致且有数据时计算。
- 萌芽/成长/成熟/收缩等阶段属于有依据的判断，结合需求、渗透率、竞争、供给和商业化迹象；不根据一条融资新闻或单一年份增速给全行业定性。
- 不同细分可能处于不同阶段；未来空间用公开假设和情景表达，不强制给出市场天花板或预测值。

### 2.2 value_chain：产业链、价值分配与议价关系

- 按实际结构选择线性产业链、服务交付网络或平台生态；不强制所有行业套用"原材料 → 制造 → 渠道 → 终端"的单线模型。
- 用简表说明关键环节：角色、提供的价值、向谁收费/向谁采购、关键资源、替代难度、议价依据、对应证据。绘图时用标签区分产品/服务流和资金流。
- 重点回答谁控制稀缺资源、客户入口、标准或关键能力；哪些环节存在瓶颈；谁可以替代谁；一处成本或需求变化可能传导到哪里。
- 价值创造、企业收入、会计利润和议价能力分别讨论。利润分布需要可比数据，不能凭产业链位置排序；没有可比数据时给影响因素和待验证假设。**不可把"上游通常利润低""终端越近附加值越高"内置为默认结论**——材料明确显示某上游环节议价更强时，遵循材料。

### 2.3 business_model：商业模式六要素

围绕客户、提供的价值、收入机制、成本结构、盈利条件、核心能力六项分析。收入机制可以是销售、订阅、佣金、广告、增值服务、项目服务或组合；按证据选择，不要求行业只有一种模式（订阅与项目收入并存是合法状态，不必二选一）。

选一个有资料支持的代表性交易，说明购买者为什么付款、按什么单位收费、交付什么、履约成本和主要约束是什么。区分获取收入、产生利润和回收现金，不把"有订阅收入"直接写成"持续盈利"。

指标服务于问题，按研究对象选择，不是四类行业的必填指标集：

| 研究对象/问题 | 可选指标方向 | 使用限制 |
|---|---|---|
| 制造和实物产品的经营条件 | 毛利率、产能利用率、库存/应收周转 | 样本、财年、产品组合和会计口径需要匹配 |
| 软件和订阅服务的持续性 | 续费/留存、毛利率、获客回收期、LTV/CAC | 定义、客户群和时间范围需公开，数据不足不硬算 |
| 项目与咨询服务的交付约束 | 单项目收入/成本、交付周期、人员利用率、回款 | 不能把报价直接当作实际收入、利润或回款 |
| 平台业务的收入形成 | 交易量、收费比例、收入、履约或补贴成本 | 区分交易总额与平台确认收入 |

Quick 通常选 1—3 个最相关指标或关键驱动；没有数据时解释机制与缺口。ROE 等资本回报指标只在相关任务且有可比数据时使用，不默认进入每份行业入门报告。

### 2.4 competition：竞争生态与关键控制点

- 除直接竞争者外，按实际相关性纳入替代方案、供应商、渠道、互补产品、平台、用户及监管/标准制定角色。一家公司可能同时是竞争者和合作伙伴，说明关系发生在哪项业务，不强行给每家公司一个永久标签。
- 从四个角度看格局：市场范围与需求变化、集中度、进入/转换壁垒、已观察到的竞争方式。集中度需要同市场、同期的份额证据；企业知名度或搜索排序不能替代份额——**只有品牌名单、没有份额数据时，不编造集中度、CRn 或垄断/寡头结论**。
- "龙头、挑战者、跟随者"只在所研究范围有证据时使用，不强制分配角色。"垄断、寡头"等判断必须区分经济结构描述与法律认定。
- 进一步解释谁影响定价、谁控制客户触点、谁掌握资源，以及增长来自新增需求还是份额转移。完整公司 SWOT、逐项价格/功能比较交给后续竞品研究（见 [SKILL.md](../SKILL.md) 的 `competitor-brief.md`）。

### 2.5 trends_risks：趋势、风险与影响路径

- 从政策、技术、需求、渠道、供给或成本变化中选择与任务最相关的因素，不要求六类全部出现。
- 将关键变化写成"变化事实 → 可能机制 → 受影响环节 → 业务影响 → 观察指标 → 反证或失效条件"。事件日期、生效日期和数据时期分开；官方政策内容与其行业影响推断分开。
- 影响路径可以跨维度建立联系（例如成本变化可能同时影响 `business_model` 的盈利条件与 `competition` 的定价行为），用 `basis_claim_ids` 和 `rationale` 记录依据，`dimensions` 可以同时打多个标签。
- 没有足够因果证据时使用条件判断并引用前提；**不要把时间先后或共现写成已证明的因果关系**——只有趋势观点、没有变化事实支撑时，标为假设，不画无依据的预测曲线。
- 涉及营收、毛利率、市场份额、采购周期等，只有资料支持时给数字；单一上市公司的财务表现不能直接代表全行业；不得用"市场大、增速快"直接推导"适合用户进入"。

## 3. 关系解释：让五维连成一张图

总览表压缩五维结论后，报告正文至少用一条有依据的关系解释环节之间的联系（例如"成本上升 → 议价能力较弱的环节被迫压缩利润 → 下游价格是否传导仍需验证"）。证据不足时给出待验证路径，不能强制生成因果结论。

产业链/生态图按复杂度选择 Mermaid 或纯文本表格，不引入图片生成、前端或 PDF 依赖。关系标签或紧随其后的说明须可回溯到 `claims[].id`；假设关系明显标记，不用示意大小暗示未经证实的份额和利润。

## 4. 研究机会与影响（opportunity 用途时展开）

机会条目使用统一结构，避免写成没有依据的"建议列表"：

```text
观察到的变化或问题（引用证据编号）
→ 可能受影响的人群/企业（具体到细分，不写"所有企业"）
→ 可探索的做法（具体、可执行）
→ 资源与进入条件（资金、资质、渠道、时间）
→ 反例或失败条件（什么情况下这条不成立）
→ 下一步验证（用户可以做的最小动作，例如联系谁、查什么数据、做什么小范围测试）
```

区分三个层次，不能只证明第一层就下结论：

1. 市场是否存在这个需求（有没有人在为此困扰或寻找方案）。
2. 这个需求是否可被付费满足（是否已有人为类似方案付费，价格带大致在哪）。
3. 用户本人是否具备进入条件（资源、渠道、时间、资质是否匹配）。

## 5. coverage 与 dimensions 的填写方法

- 每个维度研究结束后，把该维度的判断压缩进 `coverage.<dimension>`：`status` 由研究者判断（`covered`/`partial`/`missing`/`out_of_scope`），`claim_ids` 关联支撑该判断的主张，`note` 说明认识程度或边界，`next_question` 写下一步要验证的具体问题（没有则为 `null`）。
- `status=covered` 时，`claim_ids` 中至少要有一条 `kind != unknown` 且 `dimensions` 包含该维度的主张——这是机器可查的最低要求，但覆盖状态本身仍由研究者判断，机器不据此计算"行业掌握程度"百分比，某维度 `covered` 也不等于该维度所有指标均已获知。
- 撰写每条 `claims[]` 时顺手打上 `dimensions` 标签（可以为空数组，可以多选），这样 `report.md` 的五维总览表和 `evidence.json` 的 `coverage` 引用的是同一套证据，不用两次归纳。
